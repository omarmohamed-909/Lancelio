# SET-002 — signed-in password changes

`/settings/security` contains the account-security form, reached through the internal settings navigation. The user enters their current password, a new password and its confirmation, then reviews an explicit confirmation before submitting. It explains that all sessions, including the current one and sessions in other workspaces, end. Leaving a section with typed password fields asks for confirmation; cancelling keeps the fields in place, while confirmed departure removes them from memory. Cancelling the password-change confirmation returns keyboard focus to the review button and sends no request.

## Private HTTP contract

`POST /api/v1/settings/password` accepts exactly `{ currentPassword, newPassword }`. It requires the configured frontend Origin and a live bearer session. User, workspace and session IDs come from verified access-token claims, never request fields. All roles can change their own password. Current passwords contain 1–128 Unicode code points; new passwords use the registration rule of 15–128 code points and must differ from the current password. Passwords are not trimmed. The confirmation is a client check; both passwords are validated again in the application layer.

Success returns an empty **204**, with `Cache-Control: no-store` and a cleared refresh cookie using the existing HttpOnly, SameSite=Strict, Path=/ and production Secure/__Host policy. No hashes or password text are returned. Incorrect current passwords return **422 CURRENT_PASSWORD_INCORRECT**; invalid/extra fields use **422 VALIDATION_ERROR**; inactive authentication uses **401 UNAUTHENTICATED**; untrusted Origin uses **403 UNTRUSTED_ORIGIN**. Infrastructure failures return the existing private **500 INTERNAL_ERROR**.

## Atomic storage and credential races

The use case verifies the current Argon2 hash, creates the new Argon2 hash, then delegates to a transaction port. Mongo matches and revokes the requesting live session inside the transaction, verifies current membership/workspace, and replaces only the active user's expected hash. The same transaction records `passwordChangedAt`, increments the existing authentication fence, revokes every remaining account session and invalidates issued recovery jobs. A failure anywhere rolls back the credential and revocations together. No profile, email, role or issued document is modified.

The requesting-session write conflicts with logout/rotation; a session revoked or expired before the transaction cannot commit. Hash comparison and the existing login fence prevent login with a password verified before a change from inserting a live session afterward. Two competing changes produce only one valid new credential. A refresh may complete before revocation, but its access and refresh credentials cease to authorize subsequent requests. Previously started application requests retain their existing authorization semantics; this is not cancellation of work already in flight.

Issued recovery links cease to work after the hash changes and are invalidated in the transaction. Earlier unbound queue requests cannot create new links because the recovery worker compares their request time with `passwordChangedAt`. Recovery and signed-in change use the same user/session write fences.

## Attempt policy

A separate `PasswordChangeAttempt` collection reserves an attempt with an atomic counter before expensive verification. Each account gets **five validly shaped attempts per fixed 15-minute UTC bucket**, shared across sessions, workspaces and API instances; incorrect passwords and successful attempts both consume reservations. Invalid bodies/policies are rejected before reserving. Attempts after the cap return **429 RATE_LIMITED**, without hashing, mutation or sign-out. A TTL index removes expired buckets; enforcement compares bucket keys and does not depend on timely TTL deletion. A boundary can permit five attempts on each side of the window. This account limiter does not depend on forwarded IP headers, and does not replace the hosted IP/proxy release gate.

## Client recovery and sensitive fields

An immediate submission lock and the existing cross-tab Web Lock prevent repeated confirmation and concurrent local auth mutations. The password-change request deliberately bypasses the session manager's general 401-refresh-and-retry path: it is sent once. A confirmed success clears local tokens, invalidates pending identity reads/renewals, removes the form and notifies same-browser tabs to clear their own state without refreshing. The login page explains that the new password is required. Other devices learn of revocation on their next protected read or refresh.

A network failure, malformed success response or 5xx result clears local access and directs the user to explicitly verify by logging in with the new password, then the current password or recovery if necessary. It does not claim that the server committed, or resend the mutation. Same-browser tabs clear their state too; unrelated devices may still have valid sessions if the write never committed. The HttpOnly cookie cannot be cleared by JavaScript on a lost response; any surviving old credential remains subject to server revocation. There is no durable client retry/uncertainty flag; reload starts the normal server-checked session restoration.

Wrong current password clears that field, retains the new-password draft and focuses the enabled current-password input after render. Validation, rate and Origin errors keep editing available; explicit confirmation is required for any new attempt. Values are kept only in the mounted form/request, never localStorage, sessionStorage, analytics or logs. Leaving the page discards the password draft. The form supports password-manager autocomplete, paste, independent reveal buttons, Arabic RTL labels, field errors, keyboard focus and the existing reduced-motion policy. Short viewports scroll naturally to keep all actions reachable.

## Verification

Verified locally on 2026-10-10. `npm run check` passed: **751 API tests in 29 files**, formatting/lint, both architecture guards, application/release tool types and both production builds. Tests use isolated Mongo replica sets and fake recovery delivery; they never change the configured application's accounts or send real email. The new API suite covers 30 cases: own-account/all-role scope, different devices/workspaces and users, strict fields, Unicode/whitespace, shared/concurrent attempt counters, delivered/queued recovery invalidation, concurrency, login/refresh races, rollback, and logout/suspension/expiry/membership/reset between verification and commit.

**51 unique affected browser cases passed across batches**: 23 security cases, 23 profile regressions and five authentication/session/accessibility regressions. Projects comprise 31 Chromium cases and ten each on Firefox and WebKit. Thirty viewport cases inspect 90 editing/error/confirmation or draft/save/recovery layouts across **320×256, 390×844, 768×1024, 844×390 and 1440×900** with reduced motion. All **70 Axe scans** passed without disabled rules or violations: 47 security, 18 profile and five authentication scans. Desktop/mobile screenshots in `.cache/ui/security` were visually inspected. Functional cases cover explicit/cancelled confirmation, wrong current password and focus, cross-tab and separate-device revocation, old/new login, shared attempt cap, lost committed/uncommitted replies, double confirmation, delayed identity reads, expiry without refresh/replay, and private server failure recovery. Issued invoice data remains unchanged in the real profile regression.

The broad browser batch passed 47 of 51 cases. Four failures were selectors that needed to distinguish route-announcer alerts, password-reveal buttons and the newly added security inputs. The follow-up batch passed all five selected cases, including those four and rate-error focus. Focus after a wrong current password is applied after editing controls are enabled. Reports: `.cache/security-quality.log`, `.cache/security-api-verified.log`, `.cache/security-browser-run.json`, `.cache/security-browser-final.json/.log` and the derived `.cache/security-verification-summary.json`. The first browser report includes npm/list output before its JSON; `.cache/security-report-summary.cjs` reads both reports and rejects unresolved failures or accessibility violations.

The extended `npm run test:api-startup` smoke also passed against the actual compiled production entry point. It checks the new endpoint, revocation, old/new credential login, cleared **\__Host/HttpOnly/Secure/SameSite=Strict** cookie attributes and Mongo-loss readiness. This is a local controlled server check, not hosted TLS activation. No fresh full browser suite, physical-device certification or remote CI run is claimed; release activation gates remain in [RELEASE.md](RELEASE.md).
