# Lancelio — Epics and User Stories

القواعد: كل Story سلوك مفيد قابل للاختبار، وتتقسم Tasks تنفيذ. الشغل بالتتابع مع Story واحدة قيد التنفيذ.
الحالات: Ready / In progress / Done / Blocked. Done تعني استيفاء معايير القبول وفحوص الجودة، وليس كتابة الكود فقط.
الـSprints أهداف عمل، وليس تقديرًا زمنيًا محسومًا قبل معرفة القدرة المتاحة.

## Sprint 1 — Foundation + Authentication + Workspace

### FND-001 — أساس قابل للتشغيل والتحقق

As a developer, I can run and verify both apps consistently before adding business features.

Acceptance criteria:

- npm workspaces تفصل web وapi، وملف lock يثبت التبعيات.
- TypeScript strict مع lint وformat وفحص حدود طبقات الـAPI.
- الواجهة تتبني بنجاح والـAPI يوفر `GET /api/v1/health` بعقد JSON ثابت.
- إعدادات البيئة غير الصحيحة توقف تشغيل الـAPI دون طباعة قيم حساسة.
- الأخطاء غير المعروفة لا تعرض تفاصيل داخلية، مع حدود لحجم الطلب وHTTP security headers.
- أمر `npm run check` ينجح محليًا، وCI مهيأ لتشغيله عند push وPR.

Tasks: workspace setup; app bootstraps; HTTP error boundary; architectural guard; checks; CI; documentation.

### AUTH-001 — إنشاء حساب ومساحة عمل

As a freelancer, I can register and receive my own workspace.

Depends on FND-001. Acceptance criteria:

- اسم وبريد وكلمة مرور يتم التحقق منهم في الـAPI، مع تطبيع البريد وقيد uniqueness في قاعدة البيانات.
- حفظ password hash فقط، وعدم إرجاعه أو تسجيله.
- إنشاء User وWorkspace وowner membership كوحدة واحدة؛ فشل أي خطوة لا يترك بيانات جزئية.
- تكرار البريد يعطي خطأ آمنًا متفقًا عليه، حتى مع الطلبات المتزامنة.
- اختبارات نجاح التسجيل، الإدخال غير الصحيح، التكرار، والـrollback.

Tasks: entities and domain rules; application ports and use case; MongoDB/password adapters; HTTP mapping; database integration tests.

### AUTH-002 — تسجيل الدخول والجلسة

As a freelancer, I can sign in and retrieve my authenticated identity and authorized workspace.

Depends on AUTH-001. Acceptance criteria:

- بيانات صحيحة تنشئ access token قصير العمر وrefresh session.
- refresh token في HttpOnly cookie بإعدادات موثقة للبيئة، والنسخة المخزنة في DB hashed.
- رسالة موحدة لبيانات الدخول غير الصحيحة وrate limiting لمسارات الدخول.
- `/me` يعيد بيانات مسموحة فقط، والـprotected endpoints ترفض غياب/فساد/انتهاء التوكن.
- workspace access يتحقق من عضوية مستخدم فعالة، واختبار منع الوصول لمساحة مستخدم آخر.

### AUTH-003 — تجديد الجلسة والخروج

As a freelancer, I can keep my session active and terminate it safely.

Depends on AUTH-002. Acceptance criteria:

- rotation ذرية للتوكنات مع سياسة واضحة لإعادة الاستخدام والطلبات المتزامنة.
- refresh token منتهي أو ملغي لا يجدد الجلسة.
- logout يلغي الجلسة في الخادم ويمسح الكوكي؛ أثره على access token الحالي موثق.
- اختبارات rotation، replay، expiry، logout، وإعدادات cookie/CSRF.

### WEB-001 — التسجيل والدخول وDashboard محمية

As a freelancer, I can complete authentication from the browser and open my workspace dashboard.

Depends on AUTH-003. Acceptance criteria:

- forms عربية/RTL قابلة للاستخدام بالكيبورد، مع loading/errors ومنع الإرسال المتكرر.
- session handling لا يحفظ tokens حساسة في localStorage.
- dashboard تعرض هوية ومساحة المستخدم الفعلية؛ API يفرض الصلاحيات حتى لو تم تجاوز حماية الواجهة.
- انتهاء الجلسة وإعادة تحميل الصفحة والخروج لهم سلوك واضح.
- end-to-end journey: register → dashboard → logout → login، مع اختبار رفض الوصول غير المصرح.

### WEB-002 — حركة وتفاصيل بصرية لمساحة الشغل

As a user, I can navigate a distinctive Arabic interface with motion that clarifies state and keeps controls usable.

Depends on WEB-001. Acceptance criteria:

- هوية بصرية مرتبطة بورق الاتفاق والتسليم والفاتورة، وكلام مباشر بدل العبارات المتكررة.
- دخول متدرج للعناصر وتفاعل للأزرار والحقول، بدون تعطيل الإرسال أو تغيير أبعاد الصفحة.
- تقليل الحركة يوقف الأنيميشن والانتقالات ويترك المحتوى ظاهرًا.
- قائمة الموبايل تدعم Escape وTab، وتعيد التركيز بعد الإغلاق؛ الخلفية inert والـscroll مقفول أثناء فتحها.
- القائمة تتقفل عند تغيير المقاس للكمبيوتر، ولا تتسبب في بقاء الخلفية معطلة بعد استعادة الجلسة.
- اختبارات المتصفح تشمل الحركة العادية وتقليلها، مع صور نهائية وفيديو مراجعة، وفحوص البناء ناجحة.

### WEB-003 — هوية أوضح وتفاصيل واجهة متماسكة

As a freelancer, I can use a readable Arabic workspace with a consistent visual identity and quieter editing screens.

Acceptance criteria:

- خط عربي محلي بأوزان واضحة، مع ترخيصه، وتوكنز واحدة للألوان والمسافات والـfocus.
- علامة خاصة بالمشروع، وتكوين متماسك للدخول والقائمة ولوحة البداية والعملاء والعروض.
- محرر العرض يظهر كوثيقة واحدة؛ اختيار العميل يختصر بعد الاختيار مع تغيير واضح وعودة تركيز صحيحة.
- الحفاظ على الرحلات الفعلية والعزل ورسائل الخطأ والتنقل بالكيبورد وreduced motion.
- مراجعة الصور على desktop/mobile؛ نجاح الـlint والـtypes والبناء ورحلات المتصفح.

### WEB-004 — فحص الاستجابة عبر محركات المتصفح

As a freelancer, I can use the current workspace and public agreement screens on narrow, tablet, desktop and landscape layouts without losing content or controls.

Acceptance criteria:

- 25 مقاسًا بعرض 320–1920 CSS px، تشمل جوانب نقاط التحول والوضع الأفقي والارتفاع القصير.
- نفس الرحلات على Chromium وFirefox وWebKit؛ لا overflow أفقي للصفحة مع الأسماء والروابط والعناوين الطويلة والأسعار الكبيرة.
- أهداف الأزرار للمس ≥44×44، وحقول الكتابة بارتفاع ≥44 وخط ≥16؛ قيمة السعر والكمية في بيانات الضغط تظهر كاملة.
- جدول الأسعار يتمرر محليًا مع وصف واضح وإتاحة الكيبورد، والقائمة تتيح الوصول للخروج على الارتفاع القصير.
- تغيير الاتجاه يغلق القائمة عند الانتقال للتخطيط الواسع، ويعيد التمرير والتركيز ويحافظ على نص حوار العميل.
- صور مراجعة للموبايل والتابلت والسطح والوضع الأفقي؛ نجاح فحوص الجودة ورحلات المتصفح الحالية.
- توثيق المحاكاة وحدودها وقائمة فحص iPhone/Android الفعلية قبل الإطلاق؛ الاختبارات لا تدّعي تغطية كل جهاز.

Tasks: cross-engine viewport audit; long-content fixes; touch input policy; accessible table scrolling; live reflow checks; screenshots and verification guide.

## ترتيب التنفيذ الحالي

تم تنفيذ AUTH-004 وتجهيز REL-001 والتحقق المحلي منهما. تفعيل الاستضافة وResend واختبار وصول رسالة حقيقية يظلان شروطًا قبل public beta ضمن REL-001. **SET-001 وSET-002 وSET-003 اكتملت**؛ التحقق موثق في [PROFILE.md](PROFILE.md) و[ACCOUNT-SECURITY.md](ACCOUNT-SECURITY.md) و[WORKSPACE-SETTINGS.md](WORKSPACE-SETTINGS.md). حزمة الإعدادات الثلاثة مكتملة، ولا يعتبر ذلك تفعيل الاستضافة الفعلية.

**REL-001 جاهزة لاستكمال التفعيل**: تجهيز Vercel مع خدمة Node مستقلة، proxy من نفس origin، readiness، رحلة وإتاحة وHTTPS production smoke ونسخة BSON مشفّرة واستعادة آمنة. التفعيل على الاستضافة الفعلية وResend والتحقق من trusted proxies وحدود المعدل وإدارة النسخ والأجهزة الحقيقية تظل شروط إصدار مفتوحة. التفاصيل والأدلة في [RELEASE.md](RELEASE.md).

## Settings — Profile, Security and Workspace

الإعدادات تتقسم لستوري صغيرة؛ تعديل البروفايل مستقل عن استرجاع كلمة المرور AUTH-004. البداية SET-001، ثم أمان الحساب وإعدادات المساحة. شاشة إعدادات واحدة؛ تبويبات لا تظهر كأزرار بلا وظيفة قبل تنفيذ الستوري الخاصة بها.

### SET-001 — صفحة الإعدادات وتعديل البروفايل

As a member, I can open my settings, review my account details and update my display name.

Depends on AUTH-003 and WEB-001. Acceptance criteria:

- رابط واحد للإعدادات في قائمة مساحة العمل، وصفحة /settings؛ قسم البروفايل أول قسم منفذ، بلا صفحات أو controls وهمية.
- عرض الاسم والبريد والدور الحالي، وتعديل الاسم الشخصي فقط في هذه الستوري. البريد للقراءة مع توضيح أن تغييره يحتاج تحققًا منفصلًا؛ الصورة تظل بالأحرف الأولى الحالية.
- الاسم بنفس قواعد التسجيل: 2–100 حرف Unicode بعد trimming، والتحقق في الباك. المستخدم من الجلسة فقط، دون قبول userId أو role أو status أو workspace أو حقول أمان من الطلب.
- صلاحية التعديل تخص المستخدم نفسه لكل الأدوار؛ بيانات البروفايل مشتركة بين مساحاته، ولا تسمح هذه الصفحة بتعديل بيانات أعضاء آخرين.
- حفظ بنسخة حالية وCAS لمنع استبدال تعديل أحدث من نافذة أخرى. عرض حالة التحميل والنجاح والأخطاء، وتحذير قبل مغادرة نموذج تغير ولم يحفظ.
- نجاح الحفظ يحدّث بيانات الهوية والاسم والأحرف الأولى في الهيدر والقائمة والنظرة العامة، ويظل بعد reload. الفواتير والعروض والاتفاقات الصادرة تحتفظ بنسخها المحفوظة.
- نتيجة حفظ غير مؤكدة أو تعارض تتطلب قراءة الحالة الحالية قبل كتابة جديدة؛ لا إعادة حفظ تلقائية بسبب الشبكة، ولا فقد للنص المكتوب دون مراجعة.
- دعم RTL والكيبورد والتركيز والمقاسات القصيرة وreduced motion. اختبارات العزل بين المستخدمين، التحقق والتزامن والتعافي والحفظ الفعلي وتجدد الهوية.

Tasks: scoped profile port and use cases; versioned user adapter; private HTTP contracts; settings page/form; identity refresh; API/browser verification; documentation.

### SET-002 — أمان الحساب وتغيير كلمة المرور

As a signed-in member, I can change my password after proving knowledge of my current password.

Depends on SET-001 and AUTH-003. Acceptance criteria:

- قسم أمان الحساب في نفس الإعدادات: كلمة المرور الحالية، الجديدة وتأكيدها. هذا تدفق مستخدم مسجل الدخول، مستقل عن نسيان كلمة المرور AUTH-004.
- التحقق من الحالية في الخادم، وتطبيق قواعد كلمة المرور الحالية على الجديدة، دون تخزين/طباعة النص أو إرجاع الـhash. لا تعديل بريد أو دور من هذا الطلب.
- تأكيد صريح يوضح أن تغيير كلمة المرور سينهي جلسات الحساب على كل الأجهزة، بما فيها الجلسة الحالية؛ بعدها الدخول بالجديدة مطلوب.
- تحديث الـhash وإلغاء الجلسات كوحدة ذرية؛ حماية من تغييرات متزامنة ومن تجديد/إنشاء جلسة اعتمادًا على كلمة المرور القديمة أثناء التغيير.
- حد لمحاولات التحقق، واستجابات آمنة، ومنع الإرسال المتكرر. نجاح مؤكد يمسح الحقول وينهي الجلسة المحلية؛ نتيجة غير مؤكدة لا تعيد إرسال الطلب وتوجّه لإعادة الدخول/التحقق.
- اختبارات كلمة حالية خاطئة، التحقق، الإلغاء على أكثر من جهاز، سباق refresh/login، الـrollback، انتهاء الجلسة والتعافي والكيبورد والتجاوب.

Tasks: password-change use case/transaction port; session invalidation and credential race policy; HTTP validation/rate limit; confirmed security form; integration/browser tests.

### SET-003 — إعدادات مساحة العمل

As a workspace owner, I can change my workspace's display name without changing its identity or saved agreements.

Depends on SET-001. Acceptance criteria:

- قسم مساحة العمل في الإعدادات؛ owner وحده يعدّل الاسم. admin/member يشاهدان الاسم ودورهما دون صلاحية تعديل، والباك يفرض ذلك.
- الاسم بنفس قواعد تسجيل المساحة؛ workspace والعضوية من الجلسة الحالية، ولا قبول owner/plan/slug أو معرف مساحة بديل من الطلب.
- حفظ بنسخة وCAS، مع قراءة صريحة عند التعارض أو فقد الرد. هوية المساحة وslug والعضويات والروابط لا تتغير عند إعادة التسمية.
- تحديث اسم المساحة الحالي في الواجهة بعد الحفظ وreload؛ النسخ المحفوظة في عروض وفواتير واتفاقات سابقة لا يعاد كتابتها.
- اختبارات الدور والعضوية الحالية والعزل والنسخ والتعافي، والتجاوب مع اسم مساحة طويل في القائمة الجانبية.

Tasks: workspace settings port/use case; owner policy and CAS adapter; private HTTP contract; settings form/identity refresh; API/browser checks.

تغيير البريد مع تأكيد العنوان الجديد، وصورة البروفايل مع تخزين ورفع ملفات، لهما ستوري لاحقة منفصلة قبل إتاحة controls لهما. لا يدخلان ضمن SET-001 ولا يتغير سلوك الدخول ضمن تعديل الاسم.

## Definition of Ready

سلوك واضح، معايير قبول، حالات الخطأ، dependencies، وقرارات مفتوحة محسومة بما يكفي للتنفيذ.

## Definition of Done

- جميع معايير القبول مستوفاة، واختبارات السلوك والمخاطر المهمة ناجحة.
- لا `any` ولا bypass لفحص الطبقات، ولا أسرار/بيانات حساسة في الاستجابات والـlogs.
- `npm run check` ناجح، وتحديث التوثيق و`.env.example` عند تغيير العقود/الإعدادات.
- تسجيل حدود التنفيذ بدقة؛ تشغيل CI على GitHub لا يُدّعى قبل وجود remote وrun فعلي.

### PRP-002 — مشاركة نسخة مراجعة من العرض

- كل عضو حالي يدير مشاركة عروض مساحته؛ أول إصدار يحوّل draft إلى sent ويثبّت المحتوى في كتابة ذرية واحدة مع مطابقة version.
- رابط واحد حالي لكل عرض؛ صلاحية 1–30 يومًا (الواجهة افتراضيًا 7)، والتجديد يبطل السابق فورًا. إلغاء الرابط لا يعيد العرض إلى draft.
- token عشوائي 256-bit؛ التخزين digest فقط، وإرجاع السر عند الإنشاء فقط. لا استرجاع للرابط من GET؛ فقده يتطلب تجديدًا واضحًا.
- صفحة العميل مستقلة عن الجلسة، وتعرض اسم المقدّم والعميل/الشركة والبنود والأسعار والنطاق والشروط فقط؛ لا IDs أو بريد/هاتف أو metadata داخلية.
- السر في fragment الرابط، وقراءة الـAPI عبر POST body بدون cookies/access token. الردود no-store، والصفحة noindex/no-referrer.
- المنتهي/الملغي/غير المعروف نفس 404 آمن؛ صلاحية الرابط تُفحص عند كل قراءة، ولا تعتمد على حذف TTL. القراءة العامة محدودة الطلبات.
- مراجعة صريحة قبل أول إصدار؛ لا إرسال تلقائي لرسائل. فقد رد mutation يمنع التكرار ويطلب قراءة الحالة، والتعارض يطلب تحميل النسخة ومراجعتها.
- اختبارات حقيقية للعزل والتزامن وقفل المحتوى/فشل الكتابة، ورحلات المتصفح للمشاركة والنسخ والتجديد والإلغاء وانتهاء الصلاحية والكيبورد وreduced motion والموبايل.

- الواجهة تمنع الإرسال المكرر، وتطلب قراءة الحالة بعد نتيجة غير مؤكدة؛ إعادة التأكيد بعد القراءة تكمل نفس المحاولة في الذاكرة، بدون إعادة إرسال تلقائي.
- صفحة /projects/:id تعرض الاتفاق المقبول لأعضاء نفس المساحة فقط؛ إدارة المشاريع والقائمة والإنشاء اليدوي وتغيير الحالة في PRJ-001.

### PRJ-001 — قواعد التنفيذ

- قائمة المشاريع وتفاصيلها وإنشاؤها يدويًا لكل عضو حالي في المساحة؛ الـworkspace من الجلسة فقط.
- إنشاء يدوي بعنوان 2–120 حرف Unicode ووصف اختياري حتى 3000، وعميل نشط من نفس المساحة. المشروع يبدأ نشطًا، version 1.

- الحالات: active → on_hold/completed/cancelled؛ on_hold → active/cancelled؛ completed/cancelled نهائيتان. تغيير الحالة لا يغيّر البنود أو الأسعار أو الشروط أو قرار العرض.

- صفحات ثابتة 25 مع cursor، فلترة حسب الحالة، تصفير الصفحات وإلغاء النتائج القديمة عند تغيير الاختيار. لا عدّ شامل أو تقدم وهمي.
- تأكيد واضح قبل تغيير الحالة، خصوصًا الحالات النهائية؛ دعم الكيبورد والتركيز والإعلان عن نتيجة الحفظ وreduced motion.
- فقد نتيجة الإنشاء يمنع الإعادة ويتيح مراجعة القائمة. تعارض/فقد نتيجة الحالة يمنع الكتابة حتى قراءة الحالة الحالية صراحة؛ لا replay تلقائي بسبب انقطاع الشبكة.
- فهرس فريد جزئي لمصدر العرض يسمح بأكثر من مشروع يدوي، مع تركيب البديل قبل إزالة الفهرس القديم المحدد. لا حذف سجلات أثناء الترحيل.
- اختبارات transaction/rollback والعزل والتزامن والترحيل والقائمة والواجهة والمقاسات الصغيرة؛ المهام وحساب التقدم في TSK-001/TSK-002.

### TSK-001 — قواعد التنفيذ

- مهام خاصة بالمشروع ومساحة العمل؛ كل عضو حالي يديرها، والمساحة من الجلسة فقط. لا مشاركة عامة في هذه الستوري.
- العنوان 2–120 حرف Unicode بدون control characters، والوصف اختياري حتى 2000، والأولوية low/normal/high. البداية todo وأولوية normal.
- الحالات todo/in_progress/done، مع إمكانية إعادة فتح المنتهي. النقل يحدد الحالة ومهمة تسبقها في نفس العمود أو نهاية العمود؛ ترتيب باقي المهام ثابت.
- حتى 200 مهمة حية للمشروع، ولوحة محدودة تقرأ كاملة دون pagination. الحذف نهائي مع تأكيد ويترك المشروع والاتفاق كما هما.
- version تخص اللوحة كلها وإلزامية لكل كتابة. اللوحة غير المحفوظة تبدأ 0؛ كل تغيير ناجح يزيدها، حتى حذف آخر مهمة لا يعيدها للصفر. تعارض التزامن يرجع 409.
- transaction تحجز المشروع قبل تحديث اللوحة وتمنع سباق إغلاقه. active/on_hold يسمحان بالتعديل؛ completed/cancelled للقراءة. رقم المشروع وتاريخ تحديثه والاتفاق المالي لا تتغير بكتابة مهمة.
- فقد الرد أو تعارض النسخة يقفل الكتابة حتى قراءة صريحة؛ النص المكتوب يظل موجودًا حتى تأكيد تحميل النسخة الحالية. لا إعادة كتابة تلقائية بسبب الشبكة.
- لوحة ثلاثة أعمدة على الواسع وعمود واحد على الأصغر، وترتيب بأزرار واختيار موضع يدعمان الكيبورد واللمس. dialogs تعيد التركيز وتدعم تقليل الحركة.
- اختبارات قاعدة بيانات حقيقية للقواعد والعزل والتزامن والـrollback وحد 200، ومتصفح للحفظ والترتيب والاستعادة والمشروع المغلق والنص الطويل. حساب التقدم وclientVisible في TSK-002.

### TSK-002 — قواعد التنفيذ

- التقدم = المهام done ÷ كل المهام الحية، بأوزان متساوية؛ in_progress لا يأخذ نسبة جزئية والأولوية لا تؤثر في الوزن.
- نسبة صحيحة مقربة لأقرب عدد، بحد 99 طالما توجد مهمة غير منتهية. 100 فقط عندما تنتهي كل المهام. العدد المنتهي والإجمالي يظهران بجانب النسبة.
- عدم وجود مهام = percentage null ورسالة أن التقدم غير محسوب؛ لا 0% أو 100% مختلقة. حذف المهام يغيّر المقام لأنها قائمة العمل الحالية.
- الحساب من الخادم عند كل قراءة وكتابة ناجحة، ولا يحفظ counters إضافية. اكتمال المهام لا يغيّر حالة المشروع، والمشروع المكتمل أو الملغي يحتفظ بتقدمه الفعلي.
- clientVisible اختيار boolean مستقل، افتراضيه false للمهام الجديدة والقديمة. تعديل المحتوى أو نقل المهمة لا يغيّره. يحتاج version الحالية وتأكيدًا يوضح أن العنوان والوصف والحالة مسموح عرضها.
- تغيير الظهور يستخدم transaction وحجز المشروع ونفس حماية النسخ والعزل والفشل. المشاريع المكتملة أو الملغية تمنع تغييره مثل باقي تغييرات المهام.
- معاينة العميل عند صاحب المساحة فقط، ببيانات title/description/status وبترتيب المهام المسموح بها. تقدم المعاينة يحتسب هذه المهام وحدها دون كشف عدد أو حالة المهام الخاصة أو IDs أو الأولويات أو التواريخ.
- لا رابط متابعة عام ولا بوابة عميل في هذه الستوري؛ إعداد السماح ليس نشرًا. PRT-001 سيضيف الوصول بgrant وصلاحياته منفصلًا عن روابط العروض.
- دعم حالة الفراغ، إعادة فتح done، إخفاء/إظهار صريح، التركيز والكيبورد وreduced motion والمقاسات الصغيرة؛ فقد الرد أو التعارض يطلب قراءة صريحة قبل أي كتابة جديدة.

### INV-001 — قواعد التنفيذ

### INV-002 — قواعد التنفيذ

- مفتاح الإنشاء يقارن بصمة المحتوى الأصلي، وتعديل/إصدار سجلات INV-001 القديمة يثبت بصمتها قبل التغيير داخل نفس transaction. لا استهلاك أرقام عند التعديل أو الإصدار.
- مشاركة issued فقط برابط سري محدود للمستند، عمر 1–30 يومًا، تجديد يلغي القديم، وإلغاء مستقل دون فك قفل المحتوى. version مشتركة للتعديل/الإصدار/الرابط تمنع سباق المراجعات.
- تخزين digest فقط؛ token يرجع مرة واحدة، يوضع في fragment ويُرسل في body للقراءة العامة؛ لا cache/referrer/indexing، وحد للقراءة العامة.
- الاستجابة العامة allowlist: رقم/عنوان/نطاق/شروط/عملة/بنود/إجمالي/اسم وشركة العميل/اسم المرسل/تاريخ الإصدار/صلاحية الرابط. لا contact IDs أو workspace/project/request IDs أو بيانات تواصل أو notes أو digest.
- مراجعة صريحة للحفظ/الإصدار/الرابط غير المؤكد، ومنع إعادة الكتابة الآلية. انتهاء/تغيير الرابط أو عودة الصفحة من الخلفية يعيد التحقق ويمسح المحتوى السابق. الدفع والمبالغ المتبقية في PAY-001.

### PAY-001 — قواعد التنفيذ

- سجل خاص لكل فاتورة ومساحة؛ القراءة للأعضاء الحاليين، والكتابة على issued فقط. بيانات الفاتورة وأسعارها ورقمها ونسختها ورابطها لا تتغير بتسجيل الدفعات.
- amount نص عشري موجب بدقة عملة الفاتورة؛ لا rounding ولا عملة من الطلب ولا تجاوز المتبقي. paidOn تاريخ تقويمي صحيح بين 1900-01-01 واليوم UTC، وطريقة bank_transfer/cash/wallet/other، مرجع حتى 100 وملاحظة حتى 500.
- المدفوع مجموع الدفعات السارية بوحدات صغيرة؛ المتبقي = الإجمالي ناقص المدفوع. حالات not_issued/unpaid/partially_paid/paid منفصلة عن حالة إصدار الفاتورة. issued بإجمالي صفر = paid بدون اختلاق دفعة.
- سجل محدود 200 إدخال شامل الملغي، version مستقلة تبدأ 0 قبل أول إدخال. حفظ ذري لنسخة واحدة مع unique workspace/invoice؛ التزامن لا يسمح بتجاوز الرصيد.
- requestId UUIDv4 لكل تسجيل منطقي؛ نفس المحتوى يعيد السجل الحالي حتى مع version قديمة أو إلغاء الدفعة، ومحتوى آخر بنفس المفتاح 409. السر/المفاتيح لا تخرج في DTO.
- تصحيح الدفعة بإلغاء أثرها بسبب 2–300، مع الاحتفاظ بمبلغها وتاريخها وسبب وتاريخ الإلغاء. لا حذف أو تعديل أو refund أو بوابة دفع. إعادة إلغاء سجل ملغي مع version الحالية لا تغير التاريخ أو السبب.
- تأكيد صريح قبل التسجيل والإلغاء؛ نتيجة غير مؤكدة أو تعارض يوقف الكتابة حتى قراءة السجل صراحة، مع حفظ الإدخال ومنع إعادة الإرسال الشبكي الآلي. لا نشر للسجل أو حالته في الرابط العام الحالي.

### DSH-001 — قواعد التنفيذ

- قراءة خاصة واحدة للأعداد والأرصدة من مساحة العضوية الحالية، داخل MongoDB snapshot transaction؛ لا تعديل لأي وثيقة أو رقم فاتورة أو رابط.
- أعداد العملاء النشطين/الأرشيف، وكل حالات العروض والمشاريع والفواتير. العرض المرسل المنتهي عند موعده يظهر ضمن المنتهي دون تغيير حالته المخزنة؛ القبول/الرفض يظل نهائيًا. مهام المشاريع النشطة والمتوقفة فقط، الخاصة والظاهرة معًا، دون لوحات يتيمة أو مشاريع مغلقة.
- إجماليات منذ بداية المساحة لكل عملة لها فاتورة صادرة؛ المسودات لا تدخل الحساب. المقبوض مجموع الدفعات غير الملغاة لفواتير صادرة في نفس المساحة، والمتبقي قيمة الصادر ناقص المقبوض. لا تحويل أو جمع بين العملات، ولا تقدير مالي من المشاريع/العروض.
- تجميع Decimal128 ثم تحويل صحيح دقيق إلى نص minor units؛ الواجهة تستخدم BigInt لتنسيق الإجمالي دون فقد دقة، حتى بعد تجاوز Number.MAX_SAFE_INTEGER. حد الاستعلام ٣ ثوانٍ؛ فشل القراءة لا يتحول لأصفار.
- معيار المواعيد يستخدم الموجود فعليًا: أقرب خمسة روابط عروض مرسلة متاحة مرتبة بانتهائها. يوضح أن مواعيد تسليم المشاريع غير مسجلة؛ إضافة مواعيد التسليم تحتاج ستوري مستقلة قبل حساب تأخير التسليم.
- قراءة أولية قابلة للإلغاء، وتحديث صريح يمنع التكرار ويمسح الأرقام السابقة أثناء القراءة والفشل، دون polling أو إعادة محاولة تلقائية. تبديل هوية المساحة يعيد تركيب القارئ. الدخول والتجديد يتبعان سياسة الجلسة الحالية.
- التحقق: أرصدة جزئية/كاملة/صفرية، العملات الأربع، الإلغاء، الأرشيف، العزل واللوحات اليتيمة، مواعيد الحدود والروابط الملغاة، دفعة متزامنة أثناء snapshot، وتجميع ٩٠٬٠٧٣ فاتورة عند الحد المالي؛ رحلات المتصفح والتجاوب وحالات الفشل، وفحوص الجودة والبناء.

### PRT-001 — قواعد التنفيذ

- بوابة مستقلة لكل عميل في مساحة العضوية الحالية. كل عضو لديه إدارة العملاء يستطيع معاينتها وإنشاء/تجديد/إلغاء رابطها؛ الرابط لا يعطي جلسة عضو أو صلاحية تعديل.
- النطاق واضح قبل التأكيد: كل مشاريع العميل الحالية والجديدة، وكل فواتيره الصادرة الحالية والجديدة مع الملخص المالي؛ المسودات مستبعدة. لا اختيار فردي لوثائق في هذه الستوري، ولا مشاركة تلقائية لباقي عملاء المساحة.
- المهام لا تظهر إلا عند clientVisible=true، والتقدم من المهام الظاهرة فقط. المشاريع المغلقة تحتفظ بتاريخها الظاهر؛ المهام الخاصة/الأولوية/المعرفات الداخلية لا تدخل النسخة العامة.
- الفواتير في البوابة ملخصات: الرقم والعنوان والعملة والإجمالي والمدفوع والمتبقي والحالة والتاريخ. لا بنود/شروط/ملاحظات داخلية ولا سجل دفعات/مراجع/أسباب إلغاء. روابط نسخ الفواتير التفصيلية تظل مستقلة.
- token عشوائي ٢٥٦ bit، digest مخزن فقط، يعود مرة واحدة بعد الإصدار. Hash fragment في رابط /share/portal، ثم POST بلا cookies أو Authorization؛ انتهاء عند الحد نفسه، وتجديد يلغي القديم، وإلغاء دائم للمنحة الحالية.
- revision مستقل لكل workspace/client، وصفر افتراضي دون كتابة. أول إنشاء وتجديد يحجزان العميل النشط وCAS المنحة في transaction؛ فشل العملية يرجع الحجز. أرشفة/حذف العميل أو حذف المساحة يمنع القراءة العامة. الإلغاء يظل متاحًا للمؤرشف.
- الصفحة تقرأ المنحة والأهلية والمشاريع والمهام والفواتير والأرصدة في snapshot transaction واحدة. خمس مشاريع وخمس فواتير في الصفحة، مع مؤشرات عامة مشفرة تخص المنحة ونوع القائمة؛ المعاينة الخاصة تستخدم مؤشرات IDs موثقة. التصفح لا يغيّر نطاق العميل.
- الواجهة تعرض المعاينة، checkbox مراجعة وتأكيدًا صريحًا، ونسخًا يدويًا. النقر المتكرر ممنوع. نتيجة الكتابة غير المؤكدة تمنع المزيد حتى قراءة الحالة والمراجعة؛ التجديد بعدها إنشاء رابط جديد، وليس replay تلقائيًا.
- الصفحة العامة تلغي القراءة السابقة وتزيل البيانات عند تغير hash أو انتهاء الصلاحية أو استعادة صفحة من الخلفية؛ الفشل يوفر retry صريحًا دون polling. الإلغاء يمنع القراءات التالية؛ البيانات المعروضة سابقًا تحتاج إعادة قراءة للتحقق مثل روابط الوثائق الحالية.
- اختبارات العزل بين العملاء والمساحات، المهام الغائبة/الخاصة، الأموال الدقيقة والإلغاء، التصفح، الأيام/الحواف، السباقات والـrollback، الاسترداد والطلبات المتأخرة، وحدود المعدل؛ مراجعة المقاسات والمحركات والفحوص الكاملة.

### NTF-001 — قواعد التنفيذ

- صندوق خاص بكل مساحة، متاح للأعضاء الحاليين؛ workspace/user من الجلسة فقط. كل عضو يشاهد أحداث المساحة، وحالة القراءة تخصه وحده.
- الأحداث من الحقائق المحفوظة: قبول/رفض العرض النهائي، إصدار الفاتورة، تسجيل الدفعة وإلغاء أثرها. لا إشعار لعملية لم تلتزم؛ التسجيل الأصلي يظل موجودًا بعد التصحيح مع إشعار إلغاء مستقل.
- يشمل التاريخ الموجود قبل هذه الستوري. لا بريد/push أو بث لحظي أو scheduler، ولا اختلاق حدث لتغيير حالة مشروع بدون تاريخ محفوظ.
- معرف ثابت من نوع الحدث والمستند/الدفعة؛ replay لنفس قرار/دفعة لا ينشئ إشعارًا إضافيًا. DTO تسمح فقط بالنوع والعنوان والتاريخ والهدف وحالة القراءة ونسختها.
- قائمة 25 مع cursor موثق، مرتبة بالتاريخ ثم معرف الحدث. أربع قراءات محدودة ومتتابعة داخل snapshot واحدة، تدمج أحدث النتائج؛ العدّاد شامل غير المقروء في المساحة حتى أثناء التصفح والفلترة. الدفعات اليتيمة أو التابعة لفاتورة من مساحة أخرى لا تظهر.
- نسخة قراءة افتراضية 0 دون كتابة. تغيير الحالة يحتاج version وCAS، وreceipt فريدة workspace/user/eventId؛ تعارض 409، غياب الحدث 404. تكرار نفس الحالة بالنسخة الحالية لا يغيّر التاريخ أو النسخة. الرجوع لغير مقروء يمسح readAt.
- الجرس يوضح العدد عند آخر قراءة، مع اختصار بصري 99+ وإبقاء العدد الفعلي في وصف الكيبورد. فتح المستند لا يعلّم الإشعار كمقروء. لا mark-all ضمن هذه الستوري.
- تحديث صريح دون polling، والحفظ يتبعه قراءة جديدة من الخادم والرجوع لأول صفحة. غير المؤكد/التعارض يمسح القائمة والعداد ويوقف الكتابة حتى قراءة صريحة، دون replay بسبب الشبكة؛ 401 يتبع تجديد الجلسة المعتمد.
- حركة دخول قصيرة ومحدودة، وreduced motion، وإعلان نجاح القراءة واستعادة التركيز عند اختفاء صف من فلتر غير المقروء. النصوص الطويلة والأزرار تلائم المقاسات الصغيرة.

### AUTH-004 — قواعد التنفيذ

- رابط نسيت كلمة المرور في login؛ طلب الاسترجاع ثم كلمة جديدة وتأكيدها، مع حالات نجاح وانتهاء الرابط ونتيجة الحفظ غير المؤكدة.
- queue دائم في Mongo بنفس مسار الطلب لكل بريد صحيح؛ الوجود وحالة الحساب لا يغيران رد القبول. تشفير بيانات الإرسال، أسرار عشوائية 256-bit، hash للتوكن، 30 دقيقة من الطلب، واستخدام واحد.
- exact Origin، strict schemas، no-store، حدود IP مستقلة وحد بريد موحّد عبر instances؛ لا session/token cookies في الاسترجاع، ولا كشف recipient/link في logs.
- حفظ الباسورد واستهلاك روابط الحساب وإنهاء جميع جلساته داخل transaction واحدة، مع حماية التزامن مع login/refresh واستقلال الحسابات.
- Resend adapter قابل للاختبار؛ طابور بإيجار وإعادة إرسال بنفس idempotency key حتى الانتهاء. الخدمة disabled إلى أن يضاف المفتاح ومرسل موثق في البيئة. اختبار التسليم الحقيقي خطوة تفعيل في REL-001؛ الاختبارات المحلية لا ترسل بريدًا.
- رابط fragment يُزال من history؛ الواجهة لا تخزن السر أو تعيد الكتابة تلقائيًا. قواعد password بنفس التسجيل؛ RTL، الكيبورد، reduced motion والمقاسات القصيرة.
