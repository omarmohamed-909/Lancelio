# SET-001 — profile settings

The settings page at `/settings` contains the profile. An internal navigation opens [account security](ACCOUNT-SECURITY.md) at `/settings/security` and [workspace settings](WORKSPACE-SETTINGS.md) at `/settings/workspace`; each route displays one section and survives reload and browser Back. One workspace-sidebar entry opens settings. Members can edit their own display name, see their email and their role in the current workspace, and use the existing initial avatar. Workspace owners can independently rename their workspace. Email changes and avatar uploads remain separate stories.

## Contract and data ownership

`GET /api/v1/settings/profile` returns `{ id, name, email, version }` for the authenticated user. `PUT` at the same path accepts exactly `{ name, version }`. Both require a live bearer session and return `Cache-Control: no-store`; writes additionally require the configured frontend Origin. User identity comes exclusively from the authenticated session. Extra fields, alternative user paths and invalid revisions are rejected. All workspace roles may edit their own name.

Personal and registration workspace names are trimmed and limited to 2–100 Unicode code points. Client and server personal-name validation use the same rule. An atomic update matches the active user and their current `profileVersion`; one of two concurrent writers succeeds, while the other receives `409 PROFILE_CONFLICT`. Existing users without this field are treated as version zero; their first update increments it atomically without a separate migration. Credentials, authentication fences, sessions, email, roles and workspace identity remain unchanged.

Profile ownership is global to the account, not one workspace. Issued invoice/proposal/agreement snapshots are never rewritten. The current name/initial changes immediately in the authenticated UI; a browser BroadcastChannel asks other tabs to reload their identity, while visibility changes refresh independently. Earlier identity reads cannot overwrite a newly saved profile. Refresh rotation keeps a newer local profile if its pending response predates the profile update. No identity or access token is stored in localStorage.

## Recovery and navigation

An uncertain save, malformed success response, server failure or revision conflict blocks further writes. The form preserves the typed name and offers an explicit current-state read. The read shows the saved name beside the retained draft; the user chooses to adopt it or keep the draft for review. Keeping a different draft does not write automatically: a new explicit save uses the revision just read. Failed reads keep the draft and leave saving blocked. There is no automatic retry of an uncertain mutation. The session manager may retry an operation only after an explicit 401 and successful refresh, where authentication rejected the original request.

An immediate lock prevents repeated submits before React commits the pending UI. Late responses after unmount are ignored. Dirty forms warn on leaving through links, logout, browser Back and reload/close. Cancelling Back restores the current settings entry. Opening another tab and same-page fragment links leave the draft in place. Returning to the original name removes the dirty state. Browser confirmation wording for reload/close is controlled by the browser.

The screen uses existing colors, focus styles, Arabic typography, RTL layout, status/alert announcements and reduced-motion policy. Short screens scroll naturally so recovery actions remain reachable. Readonly email wraps long content; it is displayed as account data instead of an editable control.
