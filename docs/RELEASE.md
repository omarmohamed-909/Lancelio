# REL-001 — release preparation

Status: local release preparation is verified; REL-001 is ready for hosted activation, with all activation gates below still open. The selected topology is **Vercel for Next.js and a separate persistent Node.js API service**. `render.yaml` provides a Render example; importing it or selecting a compute plan can create a billable service and has not been done.

## Deployment configuration

| Component | Setting                     | Value                                                             |
| --------- | --------------------------- | ----------------------------------------------------------------- |
| Vercel    | Framework / Root Directory  | Next.js / `apps/web`                                              |
| Vercel    | Node.js                     | 22.x, at least 22.20                                              |
| Vercel    | Install command             | `npm ci --prefix ../..`                                           |
| Vercel    | Build command               | `npm run build`                                                   |
| Vercel    | `NEXT_PUBLIC_API_URL`       | `/api/v1`                                                         |
| Vercel    | `API_UPSTREAM_ORIGIN`       | Canonical HTTPS origin of the API, without path or trailing slash |
| API       | Build, from repository root | `npm ci` then `npm run build --workspace @lancelio/api`           |
| API       | Start, from repository root | `npm run start --workspace @lancelio/api`                         |
| API       | `NODE_ENV`                  | `production`                                                      |
| API       | `PORT`                      | Provider-supplied port; do not hardcode port 5000 on the provider |
| API       | `WEB_ORIGIN`                | Exact canonical HTTPS frontend origin, without trailing slash     |
| API       | `MONGODB_URI`               | Dedicated production Atlas database with transaction support      |
| API       | `JWT_ACCESS_SECRET`         | Strong production secret, independent of local/test credentials   |
| API       | Health check                | `/api/v1/health/ready`                                            |

Keep the monorepo root/package-lock accessible to the Vercel project. Set the two frontend variables **before building**; Next embeds the public prefix and compiles the rewrite destination into its build. Changing the backend address requires a new frontend build. Keep preview deployments on a separate API/database with their own exact origin; preview URLs must never point at production data.

The browser calls `/api/v1` on its own origin. Next rewrites the request to the separate service, retaining request body, Origin and cookie headers. The secure `__Host-lancelio_refresh` cookie consequently belongs to the frontend host. It remains HttpOnly, host-only, Path=/ and SameSite=Strict. Do not switch the browser URL to an unrelated backend domain or relax the cookie/Origin policy to work around a deployment problem. Production links generated by Resend use `WEB_ORIGIN`.

The API must run continuously to process the durable password-recovery queue. Choose an always-on service and review its price before activation; a sleeping instance or serverless request handler does not continuously process pending jobs. Mongo credentials need the application database's collection, index and transaction permissions. Configure Atlas network access for the provider's actual outbound addresses; use independent least-privilege backup/restore credentials.

`/api/v1/health` is liveness. `/api/v1/health/ready` checks the live Mongo connection with a bounded ping and returns 503 on failure, without connection details. Both are uncached. The frontend sends no-referrer, nosniff, frame denial and restricted camera/microphone/geolocation headers. No claim is made that these headers alone constitute a security audit.

## Local checks

```sh
npm run check
npm audit --omit=dev
npm run test:api-startup
npm run test:e2e
npm run test:release
node tools/release/install-database-tools.mjs
npm run test:backup
```

Set `MONGODB_TOOLS_DIRECTORY` to the bin directory printed by the installer before the backup drill. The installer downloads pinned Database Tools **100.19.1** for Windows x64 or Ubuntu 24.04 x64, verifies SHA256, and extracts into ignored `.cache/database-tools`; it does not install a system service. Other operating systems require a separately verified official tools installation. The drill uses an isolated temporary replica set, never the application's configured database. `MONGOMS_SYSTEM_BINARY` can select an existing mongod binary. Browser setup/`PLAYWRIGHT_BROWSERS_PATH` follows the README.

Run browser/build commands sequentially, with the normal Next dev server stopped: they share `apps/web/.next`. Keep localhost ports 3100, 5100 and 3443 free. `test:release` builds real Next production code with the same-origin rewrite and places a local HTTPS proxy in front of it. It generates a short-lived self-signed localhost certificate in ignored `.cache/release-tls`; only the isolated Playwright contexts ignore its certificate error. No OS trust store is modified. OpenSSL is required; Windows defaults to Git's bundled executable, overridable via `OPENSSL_BINARY`.

The release journey creates account, client, proposal, anonymous acceptance/project, completed visible task, issued/shared invoice, partial and final payment, client portal and notifications. It checks exact stored financial amounts, reload/logout and protected redirect. HTTPS mode additionally verifies secure cookie flags, refresh rotation and rejection of a foreign Origin on Chromium, Firefox and WebKit. Axe scans authentication/recovery states and the journey's forms, dialogs, workspace and public documents without disabled rules; keyboard/reduced-motion and responsive checks remain in the regular suite. Automated checks do not replace physical-device or assistive-technology testing.

Native WebKit on Windows exposes SameSite=None in cookie inspection even for explicit attributes; [Playwright's own tests account for this platform limitation](https://github.com/microsoft/playwright/blob/main/tests/library/browsercontext-cookies.spec.ts). The release test verifies the actual `Set-Cookie` Strict/Secure/HttpOnly/host-only attributes on every engine and additionally checks the cookie-store SameSite value on other platforms. It does not change the application's Strict policy or claim native Windows WebKit proves Safari's SameSite enforcement. Linux CI and real Safari remain separate checks.

The separate `test:api-startup` smoke boots the actual compiled API entry point in production with an explicitly isolated environment/database and an ephemeral port. It verifies registration/login, secure cookie attributes, live-session revocation, foreign-Origin rejection and 503 readiness after Mongo stops while liveness remains 200. Build the API first. Its test never loads application `.env` files or inherits production secrets.

## Encrypted backup and restore runbook

Copy `.env.backup.example` to ignored `.env.backup`, populate it locally or inject equivalent variables from the operations secret manager. Keep the separate 32-byte hex `BACKUP_ENCRYPTION_KEY` outside Git and separate from `JWT_ACCESS_SECRET`. Escrow the key securely alongside its key identifier; do not store the key next to the artifact. The CLI does not read the application's `.env` and never falls back to its Mongo URI.

1. Announce maintenance and stop **every API instance and recovery worker**; also stop any other writer to this database. Verify writes have stopped. A per-database mongodump without oplog is not a consistent snapshot while writes continue. Set `BACKUP_WRITES_PAUSED=yes` only after this step.
2. Provide `BACKUP_MONGODB_URI` with an explicit database name, official tools path and key. Create the backup in a private directory with a new filename:

   ```sh
   npx tsx --env-file=.env.backup tools/release/backup-cli.ts backup /private/backups/lancelio-2026-10-10.lancelio
   ```

3. Confirm success and nonzero artifact size, copy the encrypted artifact to restricted offsite storage, and restart the original service. Define the backup frequency/retention against the acceptable data-loss window; an example starting policy is daily plus pre-release copies, 7 daily/4 weekly/3 monthly copies, with monthly restore drills. This policy is documented, **not scheduled or enabled**. Atlas snapshot/PITR support depends on the selected plan and must be verified separately.
4. For a drill/recovery, use a **new offline database** named `lancelio_restore_<unique-name>` and set `RESTORE_MONGODB_URI` explicitly. Never point an application instance or worker at the target during restore. Run:

   ```sh
   npx tsx --env-file=.env.backup tools/release/backup-cli.ts restore /private/backups/lancelio-2026-10-10.lancelio
   ```

5. Decryption/authentication completes before a database connection is opened. Wrong keys, changed ciphertext, unsafe names and existing collections fail closed. The tool uses namespace remapping, restores BSON/options/indexes, reserves the empty target with a unique guard, and never supplies `--drop`. Any tool/sanitization failure leaves an **incomplete target**: keep it offline, investigate privately, then use another new database. No automatic deletion of a failed database occurs.
6. Inspect `lancelio_restore_guard.status`: success is `restored-access-revoked`. Check document counts, unique indexes, workspace invoice counters, issued snapshots, payment/correction history and balances. The automated drill verifies these, including unchanged financial history and preserved source data. Financial/proposal decisions remain recorded.
7. Restored sessions, consumed refresh tokens, password-recovery jobs and mailbox cooldown records are cleared. Proposal, invoice and portal grants are revoked and their versions increased. Users log in again and owners explicitly issue new sharing links. This prevents a backup from resurrecting previously revoked access. Review restored memberships/password state and rotate production secrets if the recovery follows an account compromise.
8. Point a **single** stopped API at the checked target, start with email delivery disabled, verify readiness/private/public behavior, then re-enable the verified sender and traffic. Do not perform destructive cleanup of the source database until the recovery has been accepted and its evidence retained.

Temporary plaintext dump/config files are confined to a uniquely created OS temporary directory and cleaned on normal completion/failure; UNIX permissions restrict the directory/files, while Windows inherits the operator's Temp ACL. Verify the operator Temp directory is private. A killed process or disk failure can leave temporary plaintext: inspect only the specifically identified `lancelio-backup-*` directory after confirming no operation is active. The encrypted format is AES-256-GCM with authenticated metadata. URI credentials are provided to Database Tools through a private YAML config, not command arguments; raw tool output and URI values are never printed by the CLI.

## Hosted activation gates

- Provision the selected API service, canonical frontend domain, isolated production database and server secrets. No deployment/account/resource has been created by this work.
- Verify the **actual** Vercel-to-provider forwarding chain and request limits. Express currently keeps `trust proxy` disabled, so limits key by the socket peer and can aggregate users behind an upstream proxy; in-memory IP counters also remain per instance. Do not enable `trust proxy=true` or trust client-supplied forwarding headers. Configure a verified trusted proxy path and shared/edge limits before admitting real users; prove spoofed headers cannot bypass limits. Mongo mailbox limits already coordinate across instances.
- Run readiness and full journey on the hosted canonical HTTPS origin, including secure cookies across Vercel rewrites, refresh/logout, foreign Origin rejection, grant revoke/renew and maintenance rollback. Local TLS success does not prove the provider's routing/headers/network policy.
- Configure `EMAIL_PROVIDER=resend`, server key and verified `EMAIL_FROM`. With an explicitly designated test mailbox, check inbox/spam delivery, disabled click tracking, HTTPS link consumption, expiry and session revocation. Local fake-mailer tests do not prove real delivery.
- Verify a restore drill using a designated staging database and an offsite copy, record timestamps, size/key identifier and recovery duration. Define backup ownership/retention and enable the chosen scheduled service separately.
- Check real iOS Safari/Android Chrome devices and keyboard/screen-reader operation. Browser-engine emulation and viewport audits are useful evidence, not proof of every physical device.

## Rollback

Keep the last passing frontend deployment and API artifact/reference. Stop traffic/writers before database-affecting recovery. Roll back the API artifact only when its schema/index expectations match the live data, and redeploy the matching frontend/proxy configuration. Do not undo financial entries by editing Mongo; use the existing auditable payment correction flow. For database recovery, follow the new-database procedure above, preserving the old database for review. Verify readiness, authentication, one existing issued invoice/balance and link revocation before restoring traffic. Do not rotate JWT secrets casually during a rollback: it also affects access-token verification and queued recovery encryption.
